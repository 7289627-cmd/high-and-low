# a10 report: performance on low-end phones

## Method
Chromium 153 headless, 390x844, CDP CPU throttle x4, artifact build via set_content, HL_TEST_FILL_MS=300. Harness: test/perf.py (rAF frame times, longtask observer, MutationObserver on #app for rebuilds, CDP Performance metrics for CPU share), test/summ.py (medians). 5 s window per state, 3 runs, base and new interleaved.
CAVEAT: the box had load average 9 to 23 (other workers), so frame times are noisy and two A/B runs disagreed in direction. The CPU shares (style%, script%) were stable. Headless Chrome has no GPU, so raster cost is overstated versus a real phone. Treat frame times as indicative only.

## Findings (facts)
- render() already skips unchanged state (JSON signature) and the 1 s clock tick only updates .tclock in place. Rebuilds in duel idle (1.2/s) are real game events at the 300 ms test bot speed (G.seq, bubble). Not a hot spot.
- Home scene: about 50 endless CSS animations. Style recalc is about 50% of main thread at x4 (pausing all animations drops it to 4%). No single group dominates (clouds, trees, flowers, bird, butterfly, beans each cost a little).
- Under every overlay (death scene, wheel, sheets) all those endless loops kept running behind the dark layer.
- kiteFrame ran at 60 fps, did innerHTML for bows, getBoundingClientRect x2 and matchMedia every frame.

## Changes (src/main.js, src/zz_a10.css)
1. kiteFrame: 30 fps cap; bows created once (3 paths, only `d` updated); skygap rect, width, reduced-motion flag cached per render (kiteStart clears cache, resize listener too); bean hand position re-read every 200 ms (bean moves about 5 px per 3.4 s); loop idles while a sheet is open. Output path strings are the same formulas.
2. New ovLoops() called from openOv/closeOv and at the end of render when #ov is open: pauses only infinite animations inside #app while a sheet or scene is up, resumes them on close. One-shot animations (HP drain etc.) are untouched. Wheel and death scenes are inside #ov so they still play fully.
3. zz_a10.css: `.hscene{contain:layout paint style}`.
No game logic or visuals changed.

## Remaining hot spots (recommendations)
1. Home scene is about 50 endless animations. Fix: cut to the visible set (drop .fnum x6, flowers sway, butterfly flap, bird flap on phones <=360 px wide or via `@media (max-width:420px) and (max-height:700px)`), or render the scenery as one pre-drawn layer. Risk: visual change, owner decision. Est. gain: largest remaining.
2. Cloud `filter: drop-shadow` x4 (ui2.css 285): replace by a duplicated pseudo shape or box-shadow on a flat cloud. Low risk, small gain, tiny look change.
3. `.puff` four stacked drop-shadows (ui2.css 348) on death scenes: short-lived, replace with border or SVG stroke. Low risk.
4. -webkit-text-stroke text (.vs, .ped-q, .dmg, logo): static, low cost; ignore.
5. Beans are inline SVG per render (6 lineup plus 5 scene beans on home). Cache charSVG strings per (color,acc,mood). Low risk, saves a few ms per home render only.
6. Duel view animates every bean (.bob, .eyes blink) forever; consider pausing blink on non-active cards. Visual change, owner decision.
7. Out of scope, noted: render() stringifies all of G on every schedule() (250 ms pubTimer); cheap now, grows with 6 players.
